      Reversibility classes

      If the agent gets it wrong, can you undo it?

      Polareyes grades every tool call from R0 to R4 before it runs, using the open Reversibility Classes spec. The class, not the model's confidence, sets how much an agent may do alone.

      R0No effect

      Nothing changes outside the agent's working context.

      actRead a file, run a SELECT, search
      R1Restorable

      Fully restorable with ordinary effort, and nobody outside saw it.

      act, then notifyEdit a file under version control
      R2Compensable

      Can't be restored, but a known fix exists at bounded cost.

      approve, or act in budgetCharge a card, then refund it
      R3Hard to recover

      Needs a human or out-of-band recovery, or changes access, credentials or availability.

      approve each timeRotate a secret, force-push
      R4Irreversible

      A disclosure, unrecoverable destruction, or a consequence that can't be recalled.

      never autonomousSend a message, transfer funds with no recall
      Try an action

      R2 · Compensable. Expensive, but a refund restores the position. Polareyes asks for approval, or lets it run inside a pre-approved budget.

      Severity scores get these backwards; reversibility doesn't. The classes are an open specification with a public registry of classified MCP tools: github.com/waghmaredb/reversibility-classes

      Sovereignty

      The decision happens somewhere. Where?

      Most AI security platforms decide in the vendor's cloud, even when data is kept in-region. Polareyes puts the control point at the pole of your own estate.

      For banks, government and critical infrastructure, the record of who allowed an agent to act should be held by the customer, not the vendor. Polareyes is built so that it is.

      Deployed where your data already lives.

      Protocols

      Model Context Protocol, local and remote. Model-provider APIs.

      Identity

      Microsoft Entra ID (OIDC) for users, teams and machine identities. OAuth on-behalf-of.

      Keys and signing

      Customer-held keys in Azure Key Vault.

      Evidence store

      Customer-held storage with evidence anchoring in Azure Blob.

      Integrations

      SIEM export and security-event webhooks. SaaS, database and model-provider connectors.

      Engineered to fail closed

      Fail-closed preflight

      A deployment passes preflight and final acceptance checks before go-live, and fails closed when it can't.

      Rehearsed recovery

      Backup and restore, plus restart and network-resilience rehearsals.

      Evidence continuity

      Immutable evidence verification, continuity checks and metadata-controlled capture.

      Signed with your keys

      Policies, approvals and evidence packages are signed with keys held in your own Key Vault.
